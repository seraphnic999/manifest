# Manifest — Project Handoff Summary

Written to hand off from a claude.ai chat session to a local Claude Code
session with no access to that chat history. Read this first, then
`README.md` and `docs/SETUP.md` for operational details.

## What this is

A personal travel planning + itinerary + expense-tracking app, replacing
the owner's previous workflow of managing trips in Google Keep notes.
Built from scratch across one long design conversation, working backward
from ~5 real past itineraries (business trips, a cruise, city breaks) the
owner shared to derive the data model, rather than guessing at features.

Single-user personal tool — no public sign-up, no multi-tenancy beyond
Supabase RLS scoping everything to `auth.uid()`.

## Stack

- **Expo + React Native + react-native-web**, via **Expo Router** (file-based
  routing). One codebase targets both web (deployed to Vercel) and,
  eventually, a native Android build (phase 2, chosen specifically because
  it reuses the same components rather than being a separate app).
- **Supabase**: Postgres (schema in `supabase/schema.sql`), Auth
  (email/password, single user), Storage (private `item-photos` bucket).
- App name: **Manifest**. Repo: `seraphnic999/manifest`.

## Design language

Deliberately not the generic "cream background + terracotta + serif" AI
look. Direction: a "departure board / boarding pass" aesthetic —
- Ink navy (`#212F3D`) for structure, warm paper (`#F3EFE6`) background,
  amber (`#C98A2E`) accent, teal (`#3B6E71`) secondary, coral for
  destructive/pending states.
- Times and confirmation codes render in a monospace font
  (`IBMPlexMono_500Medium`) — evokes an airport departure board.
- Day-view items render like ticket stubs: a dark time-column on the left,
  content to the right.
- All tokens live in `lib/theme.ts`. A standalone wireframe reference
  (`wireframes.html`, not in the app bundle) shows the original mockups.
- **Web is intentionally constrained to a ~480px centered column**
  (`app/_layout.tsx`) with neutral space on either side — the whole app is
  mobile-first by design, not a responsive web layout.

## Data model (see `supabase/schema.sql` for the authoritative version, with inline comments)

**Trip** → name, dates, `type` (business/pleasure/mixed — drives whether a
"Work" party is auto-seeded), destinations, `default_timezone`,
`custom_fields` (jsonb escape hatch), soft-delete via `deleted_at`.

**Day** → one per date in the trip's range, auto-generated by a DB trigger
when a trip is created. Has an optional `theme` (short title, e.g. "At
sea", editable in the UI).

**Item** → the core unit. Belongs to a day (`day_id`) OR is a trip-level
lodging span (see below). Key fields: `type` (enum: flight, transfer,
transport, lodging, activity, meal, bar, sightseeing, shopping, work,
other), `title`, `start_date`/`end_date` (now populated for **every**
item, not just lodging — see "Recent major fixes" below), `time_start`/
`time_end`, `timezone_start`/`timezone_end` (per-item override of the
trip's default), `status` (booked/optional/idea/pending), `sort_order`
(integer with 1000-gap spacing for cheap reordering), `booking_source`,
`confirmation_code`, `vendor`, `address`, `phone`, `link`, `notes`,
`custom_fields` (used today for `flight_number`, since flights needed a
field the schema didn't have — extension point working as designed),
`parent_item_id` (dual-purpose: links lodging check-in/out events back to
their span, AND reserved for future multi-leg sub-steps — these two uses
will need to be disambiguated before sub-steps are built), `alt_group_id`
(reserved for "pick one of" alternatives — not built yet).

**Lodging is split into two row "roles"**, sharing `type='lodging'`:
1. The **stay span** itself: `is_stay_span=true`, `start_date`/`end_date`
   cover the whole stay, shown as a fixed "STAY" banner on every day it
   spans — not part of the ordered day timeline.
2. **Check-in/check-out events**: ordinary orderable day items with
   `parent_item_id` pointing at the span. Editing the span's dates
   auto-moves these events to the correct new days (their time-of-day is
   preserved).

**ItemPhoto** → separate table (not jsonb), so multiple photos per item
can each have a caption/order. Stored in Supabase Storage, private bucket,
RLS scoped by a `{user_id}/{item_id}/filename` path convention.

**Expense** → trip-level, optionally linked to one item (`item_id`).
**Allocation** → belongs to one expense; this is where the interesting
design is. A single expense can be split into multiple allocations, each
independently optionally tagged with a `party_id` (who owes it — "Work"
or an ad-hoc person like "Mom") AND/OR a `shopping_list_item_id` (which
shopping-list entry it paid for). Default UX is one implicit
full-amount allocation per expense (no user-facing complexity) unless the
user explicitly toggles "split."

**TripParty** → ad-hoc debtors ("Mom", "Work"). "Work" auto-seeded only
for business/mixed trips.

**TripCurrency** → NIS always present (rate 1, `is_default=true`); others
added with a manually-entered rate-to-NIS. All conversion is computed at
display time from the stored rate, never persisted, so correcting a rate
later updates everything retroactively.

**ShoppingListItem** → trip-level, optionally linked to an item (e.g. "duty
free", a mall). "Bought" status is *derived*, not a stored flag — it's
true iff an allocation links to this row.

## Feature status — what's actually built and wired to real data

- Auth (Supabase email/password)
- Trip list (root screen) → Trip creation (dates via native/web date
  picker, type, destinations, default timezone with a combo-box-style
  picker sorted by UTC offset + custom entry, currencies as a matching
  combo-box)
- Trip Overview: flights list, lodging list, day list (all tappable),
  running Money total, link to Shopping — all populated from real queries,
  not placeholders
- Day view: chronological items with a "STAY" banner for active lodging,
  drag-and-drop reordering (`react-native-draggable-flatlist`), a
  day-picker pill strip for quick lateral navigation, editable day title
- Item creation: a dark icon-tile picker (9 categories; Food&Drink and
  Activity each fold two DB types behind one form with a subtype toggle)
  → category-specific form fields
- Item editing: same field set, plus delete (soft) and — for lodging spans
  specifically — date changes that cascade to move the linked check-in/out
  events
- Item details page: date/time (now shown+editable for every item type,
  not just lodging), type-specific fields (e.g. flight number), notes,
  Expenses section (add/edit/delete inline), Shopping-list section
  (add/edit inline), Photos section (deliberately last on the page — least
  commonly used)
- Money screen: total spent (converted to NIS), owed-by-party rollup,
  expense list, add/edit/delete with the full split-allocation UI
  (per-row party AND shopping-item linking)
- Shopping screen: grouped by linked-activity vs. general, bought status
  derived from allocations, add/edit/delete, "mark bought" flow reuses the
  expense form pre-linked to the shopping item
- `TripNavBar`: a small persistent pill-row (Overview/Money/Shopping) on
  every trip-scoped screen for direct lateral navigation, independent of
  back-button history
- A real `Stack` navigator (was missing entirely early on — see below)

## Not built yet

- Alternatives ("pick one of" slash-separated options, e.g. "Dinner —
  Disrepute/Cahoots/Swift") — explicitly deferred by the owner
- Multi-leg sub-steps (e.g. the Cinque Terre train-hopping chain) —
  explicitly deferred; will need its own relationship since
  `parent_item_id` is already used for lodging check-in/out linkage
- PDF itinerary export
- Trip editing (trips are currently create-only; can't extend date range,
  add/remove currencies or parties after creation)
- Android native build has NOT been produced yet — only prepared for
  (`expo-image-picker` config plugin, `expo-dev-client` dependency,
  `docs/ANDROID_LOCAL_BUILD.md` written). The owner intends to build
  locally via `npx expo prebuild` + Android Studio, NOT EAS.

## Recent major fixes (this session, roughly in order — worth knowing so they aren't re-litigated)

1. **Every item now gets an explicit `start_date`**, not just lodging spans
   — originally only lodging had dates, but the owner wanted date always
   visible/editable everywhere, and Trip Overview needed it for the
   flights list. Editing an item's date now moves it to the matching day
   (same chronological-insertion logic used everywhere else for
   `sort_order`).
2. **A widespread JSX unicode-escape bug**: `\u20aa` (₪) and similar
   written as bare JSX text or unbraced attribute strings render as
   literal backslash-text — only JS *expressions* (braces or template
   literals) interpret `\u` escapes. Grepped and fixed every instance.
3. **The root layout used `<Slot/>` instead of `<Stack/>`**, meaning there
   was no navigator anywhere and every screen's `<Stack.Screen
   options={{title}}>` call had no navigator to attach to. This was the
   prime suspect for a "blank day page" crash the owner hit, and also
   explains why there were no back buttons anywhere. Fixed by using a real
   `Stack` navigator at the root.
4. **Removed the placeholder global tab bar** (Types/Money/Shop tabs that
   existed before those became real trip-scoped screens) — dead/confusing
   leftover scaffolding, deleted. Trip list is now the plain root screen.
5. **A `TripNavBar` sizing bug**: the horizontal pill-strip nav (both this
   component and the day-picker pill strip) had padding-derived height,
   which visibly collapsed/clipped specifically on screens where the
   sibling below was a `FlatList`. Fixed by giving both an explicit fixed
   `height` instead of relying on padding.
6. **A real dependency bug, verified by actually reproducing it**: local
   `npx expo start --web` was crashing with `Font.resetServerContext is
   not a function`. Root cause: `@expo/vector-icons` (pinned too loosely
   at `^14.0.0`) was pulling in `expo-font@57.x` (a much newer,
   incompatible major) alongside the correct `12.0.10` that Expo SDK 51
   needs — two conflicting copies in the tree. Fixed via a pinned exact
   version plus an npm `"overrides"` entry forcing one `expo-font` version
   tree-wide. **This was verified with an actual clean install and a
   successful `expo export --platform web` run**, not just theorized.

## Environment / access notes for continuing locally

- The owner is on **Windows**, Node was upgraded to check compatibility
  (v24 was suspected as a contributor to build issues at one point, but
  the actual root cause turned out to be #6 above, not the Node version —
  worth confirming Node 20 LTS is still what's in use, but don't assume
  Node version is the source of future issues without evidence).
- Supabase project setup, running `schema.sql`, and running
  `seed_barcelona.sql` (a full realistic 12-day trip seeded from the
  owner's real Barcelona/cruise itinerary, used as the test fixture) are
  all documented in `docs/SETUP.md`. If the seed was run before the
  `start_date`-on-every-item fix, existing seeded data needs either a
  re-seed or this backfill:
  ```sql
  update items set start_date = days.date from days
  where items.day_id = days.id and items.start_date is null;
  ```
- GitHub push access in the claude.ai session was via a short-lived
  fine-grained PAT pasted into chat each session — not available to this
  Claude Code session; assume normal local git credentials apply here
  instead.
- Vercel deployment: build command `npx expo export --platform web`,
  output directory `dist`, needs `EXPO_PUBLIC_SUPABASE_URL` and
  `EXPO_PUBLIC_SUPABASE_ANON_KEY` set as environment variables in the
  Vercel project (documented in `docs/SETUP.md`).
